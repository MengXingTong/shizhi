# 验证版实施决策 · 2026-11-03

## 为什么没有立刻迁移 Compose / Room

正式设计中推荐 Kotlin / Compose / Room。本阶段先解决最不确定的真实接入闭环，保留已搭建的 Java 原生能力，把确认过的界面作为本地资源打包进 APK。这样能先交付可在手机上测试的安装包，不先花时间重复制作页面。

这是一项明确的阶段性决定，不把 Java/WebView 验证实现说成已经完成的 Compose 架构。若最小闭环通过，再决定保留本地界面或迁移 Compose，SQLiteOpenHelper 的结构也可向 Room 迁移。

## 实际模块

- `MainActivity`：仅允许本地 HTTPS 映射资源的 WebView，窄 JSON 桥，原生确认与诊断。
- `SourceActivity` / `SourceNavigation`：独立原视频查看；远端页无 JS 桥、不自动外跳、不使用登录成功返回。
- `SourceBinding`：视频/字幕/摘要来源的身份与指纹校验，旧数据禁播与跨视频复用防护。
- `LoginActivity`：独立官方网页登录，不挂接业务桥。验证成功后加密保存 Cookie，清理临时网页存储。
- `SecureSettings`：Keystore/AES-GCM；只返回无 Key/Cookie 的设置视图。
- `QueuePolicy`：纯 Java 的容量、预留槽位、会话代际与取消。没有请求计数上限。
- `Engine`：单生产者；条件等待，而非轮询；队列消费唤醒；空结果降频与可恢复错误；TTS 与播放控制。
- `BiliClient`：登录校验、候选、详情、字幕读取。非公开接口不散落在 UI。
- `LlmClient`：可注入传输、兼容长度参数、结构解析、ID 白名单、逐字引用/时间点验证。
- `Net`：HTTPS、直接连接优先、有限响应大小、超时、取消、不跟随重定向、POST 不重试。
- `DataStore`：SQLite、去重、收藏/过期、队列、按句进度；历史/收藏分页加载。
- `PlaybackService`：前台通知、MediaSession、音频唤醒锁、系统超时处理；不 sticky 重启。
- assets：原型视觉落地，但不携带示例摘要，不让浏览器直接发起业务网络请求。

## 已修正的试验代码问题

- 删除每轮请求上限和固定扫描总批次上限，改为持续按需生产。
- 在途提炼计入容量，停止后拒绝晚返回结果，重复开始不并发生产。
- 未提供 usage 不显示成 0。
- 非收藏的过期待播也会清理；播放中的条目暂不删除；清理后可唤醒缺货生产。
- 取消过期收藏前原生确认，不静默丢失。
- MediaSession 的播放动作不再错误地切成暂停。
- 恢复按句进度，音频焦点丢失和耳机断开会暂停。
- TTS 测试不会让首次自动播放永久保持暂停状态。
- 暂停/等待时释放不必要的前台工作和音频唤醒锁。
- 官方登录临时网页存储不作为长期凭据仓库。

## 仍然没有验证的事项

1. 用户手机是否能完成官方网页登录及 Cookie 验证。
2. 已登录的个人推荐端点与字幕权限是否满足当前接口约定。
3. 用户服务商/模型能否稳定返回可验证的摘要结构。
4. 设备中文 TTS、锁屏、通知、耳机、音频焦点和后台限制的实际表现。
5. Android 原生 SQLite/Keystore 的设备重启、升级与极端故障恢复。

现有自动化验证不能替代这些真机测试。优先使用功能设置的字幕诊断，不调用模型；成功后再只提炼一个视频。
## 0.1.2 行为补充

新刷取清空旧待播（移至历史），暂停/继续保留；保存偏好本身不清。来源从详情/首分P/player 绑定到不可变 Transcript、模型输入和数据库，原生最新内容优先于分页缓存。旧版未绑定摘要隔离但不删除收藏；手动费用确认后才允许修复。细节及限制见 CHANGELOG-0.1.2.md。

## 0.1.3 持续补货与体验补充

RefillLoop 是 Engine 实际使用且可在 JVM 验证的持续循环；RefillPolicy 只控制频率，绝不按空批终止。只读临时网络错误在原位置自动恢复，模型 POST 不盲目重发。正常状态、暂时等待和需处理错误分开；当前播报在诊断前，空队列显式等待新内容，偏好未应用提示，重刷确认/串行切换和进程恢复意图均见 CHANGELOG-0.1.3.md。
